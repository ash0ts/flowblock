# Application services

`api.ts` handles HTTP routing, request validation, ownership, and response shapes. `jobs.ts` reserves planning and analysis work with an idempotency lock and quota in one database transaction. `takes.ts` owns live-take lookup and the common deletion path used by the API and `maintenance.ts`.

The browser supplies authored scene, gear, and intent. Every server operation recompiles those inputs before trusting a path or validation result. Planning runs through `planner.ts` (`flowblock-planner-v1.5`); evidence-based changes run through `revision-planner.ts` (`revision-v1.4`). `planner-actions.ts` derives stage-specific action schemas from the shared vocabulary: initial planning cannot call revision tools, and revision must read findings before proposing a change. `planner-feedback.ts` supplies applicable recipe parameters, units, validation guidance, and bounded bearing-repair search.

Planning records every rejection, including the one that exhausts the repair budget. Identical rejected compiles receive a `no_progress` observation. Compiled camera height and duration must match the explicit intent within `1e-6` meters and seconds respectively; mismatches cannot enter final or partial selections. An empty finish requires an actual compile but may discard a geometry-valid shot that misses the creative brief. Budget exhaustion preserves earlier valid candidates as explicitly incomplete, unselected options. Geometry does not verify arbitrary natural-language intent. [The agent workflow guide](../../docs/agent-workflow.md) explains these boundaries and the recorded failures behind them.

Camera or operator collisions can trigger deterministic bearing search, unless the candidate changes explicit height or duration. Search retains source inputs and other overrides, checks at most twelve alternative bearings, and stops after three valid suggestions. When distance or travel was implicit, those values can change with the framing solution. Observations include actual trial parameters, rejection codes, elapsed time, and viewing-side tradeoffs. Orbit observations report camera-right or camera-left motion while facing the product, actual start/end bearings, and the signed compiled sweep after any reversal. Repair options also state whether that sweep matches the rejected candidate. A negative viewing bearing does not reverse a positive sweep; `bearingDeg` places the arc, while `reverse` reverses its traversal. The model still judges whether the brief permits the changed viewing side and may give a qualified abstention. Suggestions contain no candidate IDs and never enter the coordinator's candidate map. The model must compile its chosen option before finishing.

The six model actions and two repairs bound requested compiles to six and internal search compiles to thirty-six per invocation. Traces report `flowblock.compile_checks` and `flowblock.repair_search_compile_checks` separately; recipe-library fallback compilation is outside those counters. These limits bound deterministic work counts, not wall-clock time or model quality.

After the required evidence read, `revision-actions.ts` derives the action schema from the actual finding IDs and recipe parameters. Size and clipping findings permit only a distance experiment; measured size direction constrains its sign. Duration is available only for duration findings. An explicit `abstain_revision` returns HTTP 422 with `outcome: abstained` and no substitute plan. Invalid-action traces wrap the received argument so an empty object survives backend normalization.

Revisions receive the original saved intent, current compiled motion, applicable parameters, and units before reading the findings. They require one finding and one parameter used by the recipe. Duration findings support timing changes; spatial findings cannot support timing changes. A revision cannot remove the movement or reverse an orbit. The creator-facing explanation is generated from the validated change and finding, with physical causes left as hypotheses. Providing the original brief does not add a general semantic validator.

Both coordinators share cooperative deadline and optional-telemetry handling in `coordinator-runtime.ts`. Tracing failures cannot discard a completed result. The deadline does not guarantee elapsed time during host suspension or event-loop blocking.

Each coordinator runs in an isolated Weave async context. New API journeys persist an owned workflow ID and reuse it as the Agent Lens conversation ID across planning, worker analysis, revision, and acceptance. Independent requests and stages keep their own actual trace IDs. `workflows.ts` owns the execution ledger; the worker creates analysis attempts only when claiming a lease. See the [workflow telemetry contract](../../docs/workflow-telemetry.md). Every model request snapshots its messages before later turns change the history. Model spans record execution failures; expected action or validation rejections remain tool observations. Turns retain the final response, result source, outcome, and stop reason, including fallbacks. Agent Lens reads this same conversation data; it does not require duplicate export. See [Agent Lens](../../docs/agent-lens.md) and the [Forge service map](../../docs/forge-integration.md).

The developer view keeps the original training record separate from the broader research campaign. `campaign-summary.ts` validates the checked-in campaign snapshot, including result denominators and links to the fixed private project. It makes no live service requests. [Snapshot generation](../../training/experiments/next/campaign-snapshot.md) documents explicit attempt selection, source hashes, verified evidence, and separate development, confirmation, and creator-study states.

Plan generation creates a running job and publishes its result with a conditional database update. Analysis uses the separately leased Python worker. Cancelling completed work reports its actual state. Project writes lock the project and compare the expected version before saving a new immutable snapshot and its current name.

Revisions cite a stored analysis owned by the requester. Before publication, the server locks its live source take. Acceptance takes the same lock before updating the revision. Deletion locks the take first, removes associated revision evidence and take-linked workflow attempts, cancels and scrubs analysis jobs, and then removes media. This lock order prevents publication after deletion without holding a database transaction open during inference. Saved project versions are separate from uploaded take records.

`storage.ts` validates object keys, streams bounded uploads into unique partial files, and publishes under the take lock. Local upload URLs are relative to the caller's origin, preserving the browser hostname even when the server represents it differently; S3 upload URLs remain absolute and signed. Local playback supports range requests. Remote S3 support is an optional adapter and has not been verified against a deployed bucket.

See [operations](../../docs/operations.md) for quotas, retention, recovery, and local identity. [Generated API contracts](../../docs/openapi.json) describe the requests and responses. [The architecture guide](../../docs/architecture.md) explains the product boundaries and model roles.
